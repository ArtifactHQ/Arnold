# Solid Stack Boot Probe Design

**Date:** 2026-02-22
**Status:** Approved
**Spec Items:** SPEC-EXEC-001, SPEC-TIER-008

## Problem

The current boot verification check (`bin/rails runner 'ActiveRecord::Migration.check_all_pending!; SolidQueue::Job rescue nil'`) passes even when SolidQueue is misconfigured because:

1. `rescue nil` silently swallows the connection error
2. `ActiveRecord::Migration.check_all_pending!` only checks the primary database
3. The check never verifies that Solid Queue/Cache/Cable connect to their respective databases

This has caused `bin/dev` crashes in pipelines #92, #94, and #96. The apps boot via `rails runner` but crash immediately when SolidQueue workers start because `connects_to` is missing from `config/environments/development.rb`.

## Solution

Add a built-in `solid_stack` verification check type to VerificationRunner.

### Config Usage

```yaml
verification_checks:
  - name: "Solid stack connections"
    type: solid_stack
    required: true
```

### Implementation

**VerificationRunner** gains a `solid_stack` check type that generates and executes a Rails runner script. The script:

1. Tests `SolidQueue::Record.connection.active?` (if SolidQueue is defined)
2. Tests `SolidCache::Record.connection.active?` (if SolidCache is defined)
3. Tests `ActionCable::Record.connection.active?` (if ActionCable::Record exists as distinct class)
4. Exits 1 with descriptive error on failure, e.g.: `SolidQueue: no such table. Add config.solid_queue.connects_to in development.rb`

**Script template:**

```ruby
errors = []
if defined?(SolidQueue::Record)
  begin
    SolidQueue::Record.connection.active?
  rescue => e
    errors << "SolidQueue: #{e.message}. Add config.solid_queue.connects_to in development.rb"
  end
end
if defined?(SolidCache::Record)
  begin
    SolidCache::Record.connection.active?
  rescue => e
    errors << "SolidCache: #{e.message}. Add config.solid_cache.connects_to in development.rb"
  end
end
if defined?(ActionCable) && ActionCable.const_defined?(:Record, false)
  begin
    ActionCable::Record.connection.active?
  rescue => e
    errors << "ActionCable: #{e.message}. Check cable DB configuration"
  end
end
if errors.any?
  $stderr.puts errors.join("\n")
  exit 1
else
  puts "All Solid stack connections OK"
end
```

### Why Built-In

The recurring `rescue nil` pattern proves that user-written probes are fragile. A built-in type ensures correctness, generates descriptive errors, and adapts to which Solid gems are present.

### Tier Gate Integration

When the check fails, the tier gate receives `success: false` with the descriptive stderr message. Corrective tasks generated by the gate will contain the exact error, making the fix obvious to the execution agent.

### Scope Boundaries

- Does NOT validate `bin/dev` Procfile entries (future improvement)
- Does NOT validate ActionMailer, ActiveStorage, or other service connections
- Does NOT auto-fix the `connects_to` config (execution agent handles that via corrective tasks)

### Expected Impact

Would have caught the Solid Queue bug in all 3 pipeline runs. The descriptive error message gives corrective task agents the exact fix needed.
