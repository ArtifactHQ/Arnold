Orchestrate AI agents into structured software

Arnold Pipeline turns a natural-language description into a specification, breaks it into dependency-ordered tasks, dispatches them to your coding agent of choice, and iterates until the implementation matches the spec.

Get Started → How It Works
$ gem install arnold_pipeline

Quick Start #

Arnold is not another AI code editor. It doesn't write code itself. It automates the methodology that separates good AI-assisted development from chaotic AI-assisted development: structured specs, dependency-ordered execution, quality gates, and iterative refinement. The actual code generation happens through whatever coding agent you plug in.

bash 
$ gem install arnold_pipeline

# Set your API keys
$ export ANTHROPIC_API_KEY=sk-ant-...   # or OPENAI_API_KEY=sk-...
$ export GITHUB_TOKEN=ghp_...

# Run the full pipeline
$ arnold run "Build a todo list app with user auth and real-time updates" \
    --repo owner/repo

# Trigger a specific coding agent on generated issues
$ arnold run "Build a todo list app" --repo owner/repo --issue-mention "@claude"

# Using OpenAI instead of Anthropic
$ arnold run "Build a todo list app" --provider openai --repo owner/repo
bash 
$ gem install arnold_pipeline
$ npm install -g @anthropic-ai/claude-code

$ export ANTHROPIC_API_KEY=sk-ant-...

$ mkdir my-app && cd my-app && git init
$ arnold run "Build a todo list app with user auth and real-time updates" \
    --execution-provider claude_code \
    --claude-code-repo-path .

Partial execution

Don't want to run the whole pipeline at once? Stop at any stage and pick up where you left off.

bash 
$ arnold run "Build a todo list app" --stop-after tasks  # Review spec + tasks first
$ arnold resume 1                                       # Continue from where you left off
$ arnold resume 1 --stop-after executed                  # Resume and pause again later

The CLI stores runs in a SQLite database at ~/.arnold_pipeline/pipeline.sqlite3, created automatically on first use.

How It Works #

Arnold follows a structured, multi-stage workflow. Each stage feeds into the next, with quality gates and a feedback loop that iterates until the implementation aligns with the spec — or flags decisions for human review.

1
Library Manager
Matches your description to a persona + recipe via keyword matching
2
Spec Generator
NL input + persona + recipe → OpenSpec-format Markdown with GIVEN/WHEN/THEN scenarios
3
Task Breaker
Spec → 5–20 dependency-ordered tasks with tier assignments
4
Executor → Tier Gate
Dispatches tasks tier-by-tier to your chosen provider. Each tier is validated before advancing.
5
Analyzer
Compares diffs against spec → decision + confidence score
Done ≥70% confidence → merge & complete
Iterate Tasks Replace tasks, re-execute
Iterate Spec Structured deltas, re-break

Agents are stateless service objects — input in, output out. The Orchestrator owns state, persistence, and the feedback loop. Max 3 iterations, then stop. Confidence below 70% flags for human review.

Execution Providers #

The execution provider controls how tasks are dispatched and how results are collected. Everything else — spec generation, task breakdown, analysis, tier gating — works the same regardless of provider.

GitHub Default
Async — team workflows & CI
  • Creates GitHub Issues for each task
  • Polls for PRs that reference the issue
  • Merges PRs via GitHub API
  • Requires GITHUB_TOKEN + coding agent on repo
Claude Code
Sync — solo dev, rapid iteration
  • Dispatches directly to Claude Code CLI
  • Each task runs in an isolated git worktree
  • Captures diffs immediately — no polling
  • Requires ANTHROPIC_API_KEY + local repo

The llm_provider / llm_api_key config is required regardless of execution provider — it powers spec generation, task breakdown, analysis, and tier gate checks. The execution provider only controls how tasks are dispatched.

Coding Agent Setup #

This section applies to the GitHub execution provider. When using Claude Code, Arnold dispatches directly — no agent setup needed.

Arnold creates GitHub Issues but doesn't write code itself — it expects a coding agent on your repo to pick up issues, work on branches, and open PRs. Without this, Arnold will create issues and then time out waiting for results.

What Arnold creates

Each issue body contains the task description, prior implementation context (if context_propagation_enabled), an agent mention (if configured), dependency references, and a pipeline run footer.

What Arnold expects back

A pull request whose title or body contains #<issue_number>. Arnold scans all repo PRs for this substring — no special labels or webhooks required.

Open PR with a diff = task resolved (merged after tier completes). No PR + closed issue = task failed. Only WIP comments = still polling. Substantive comments = task resolved.

Agent options

Create .github/workflows/arnold-agent.yml:

yaml 
name: Arnold Agent (Claude Code)

on:
  issues:
    types: [opened]

jobs:
  solve:
    if: contains(github.event.issue.body, 'Pipeline Run')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: read

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Create branch & run
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          BRANCH="arnold/issue-${{ github.event.issue.number }}"
          git checkout -b "$BRANCH"
          claude -p "Work on issue #${{ github.event.issue.number }}. ${{ github.event.issue.body }}"
          git push origin "$BRANCH"
          gh pr create \
            --title "Resolve #${{ github.event.issue.number }}" \
            --body "Resolves #${{ github.event.issue.number }}" \
            --head "$BRANCH"

Add ANTHROPIC_API_KEY to your repo's Settings → Secrets → Actions.

Same workflow structure, swap in the OpenAI Codex CLI:

yaml 
# Key differences from the Claude Code version:
- name: Install Codex
  run: npm install -g @openai/codex

- name: Run Codex
  env:
    OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
  run: |
    codex --approval-mode full-auto \
      -q "Work on issue #${{ github.event.issue.number }}. ..."

The shortest path — no workflow file needed. GitHub Copilot Coding Agent can be assigned to issues directly.

  1. Enable Copilot Coding Agent on your repo (requires Copilot Enterprise or Business with agent support)
  2. Set config.github_issue_mention = "@copilot"
  3. Copilot automatically picks up issues, works on a branch, and opens a PR

No workflow file, no API keys beyond your existing Copilot subscription.

Tips

  • PRs must reference the issue number — Arnold matches #<issue_number> as a substring. Use formats like Resolves #42.
  • Set polling_timeout generously — complex tasks may take 5–10 minutes. The 30-minute default works for most cases.
  • Dependency ordering is automatic — later-tier issues won't appear until earlier tiers merge.
  • Context propagation helps your agent — each issue includes a summary of prior tiers, so the coding agent doesn't have to guess what exists.

Tier Gating & Context Propagation #

Tasks execute tier-by-tier (tier 0 first, then tier 1, etc.). After each tier's results merge, two optional features kick in:

Tier gate check

When tier_gate_enabled is true, an LLM reviews each tier's diffs and decides pass/fail. On failure, corrective tasks are created and re-executed, up to max_tier_retries times. If retries are exhausted, the pipeline pauses for human review. Gate checks are lenient by default — only critical, build-breaking issues cause a failure.

Context propagation

When context_propagation_enabled is true, each gate check also produces a 2–3 sentence summary of what was built. These summaries accumulate across tiers and are prepended to the next tier's task bodies, giving coding agents explicit context about what already exists.

Both features use a single LLM call per tier. If the gate check errors (e.g. LLM timeout), it's treated as non-fatal and the pipeline continues.

ruby 
# Disable both for faster execution (no per-tier LLM calls)
config.tier_gate_enabled = false
config.context_propagation_enabled = false

# Keep context but skip gate enforcement
config.tier_gate_enabled = false
config.context_propagation_enabled = true

# Pause immediately on first gate failure (zero retries)
config.max_tier_retries = 0

Post-Merge Hooks & Verification Checks #

After each tier merges, Arnold can run post-merge hooks to fix derived files and verification checks to validate the build. These run locally, so they apply to the Claude Code provider. For GitHub, set claude_code_repo_path to keep the local repo in sync.

Post-merge hooks

Hooks trigger when changed files match configured glob patterns. Use them to regenerate derived files after tier merges.

ruby 
config.post_merge_hooks = [
  {
    name: "Regenerate database schema",
    trigger_paths: ["db/migrate/**/*.rb"],
    command: "bin/rails db:prepare && bin/rails db:schema:dump",
    commit_paths: ["db/schema.rb"],
    commit_message: "Regenerate schema.rb after tier merge"
  },
  {
    name: "Bundle install on Gemfile changes",
    trigger_paths: ["Gemfile", "Gemfile.lock"],
    command: "bundle install",
    commit_paths: ["Gemfile.lock"],
    commit_message: "Update Gemfile.lock after tier merge"
  }
]

Verification checks

Checks run shell commands to verify application health. Each check has a type (:boot, :test_suite, or :custom) and can be marked required. Required checks short-circuit on failure — subsequent checks are skipped.

ruby 
config.verification_checks = [
  {
    name: "Boot check",
    command: "bin/rails runner 'puts Rails.version'",
    type: :boot,
    required: true   # Pipeline pauses if this fails
  },
  {
    name: "Test suite",
    command: "bin/rails test",
    type: :test_suite,
    required: false  # Gate sees results but doesn't auto-fail
  }
]

Non-fatal by design. Hook and check failures don't crash the pipeline. Results are passed to the tier gate check agent, which decides whether to fail the tier (triggering corrective tasks) or pass despite issues.

Programmatic usage

ruby 
orchestrator = ArnoldPipeline::Orchestrator.new

# Full pipeline
result = orchestrator.call(nl_input: "Build a REST API for inventory management")
result.status       # => "completed"
result.tasks.count  # => 12

# Partial execution — review before continuing
run = orchestrator.call(nl_input: "Build a dashboard app", stop_after: :tasks)
run.status  # => "paused"
result = orchestrator.resume(pipeline_run: run)

# Async (via ActiveJob)
run = ArnoldPipeline::PipelineRun.create!(nl_input: "Build a dashboard app")
ArnoldPipeline::PipelineJob.perform_later(run.id)

Partial Execution & Resume #

The pipeline can be paused at any stage and resumed later — useful for reviewing intermediate results or recovering from failures.

stop_afterStops afterWhat exists when paused
:specSpec generationSpecification (markdown + structured data)
:tasksTask breakdownSpecification + 5–20 ordered tasks
:executedDispatch + result collectionTasks with external IDs, diffs, and comments
nilFull pipelineEverything including analysis iterations

How resume infers the stage

The orchestrator inspects existing data to figure out where to pick up:

StateResumes from
No specificationSpec generation
Spec exists, no tasksTask breakdown
Tasks exist, no external IDsTask dispatch
Tasks have IDs, incomplete resultsResult collection
All tasks have resultsAnalysis

Already-published tasks aren't duplicated on resume — only remaining tasks are dispatched.

OpenSpec Integration #

OpenSpec is an optional Node.js CLI that enables surgical spec merging during iterate_spec decisions. Instead of appending new requirements, OpenSpec can add, modify, or remove individual requirements in-place.

bash 
$ npm install -g @fission-ai/openspec

When installed, Arnold writes the current spec and structured deltas to a temporary workspace, calls OpenSpec to merge them, and creates a new SpecRevision with the result.

Fallback chain: If OpenSpec is installed but merge fails → structured append. If OpenSpec isn't installed or is disabled → append directly. Both paths are functional; OpenSpec just produces cleaner specs across iterations.

ruby 
config.openspec_enabled  = true       # default — use when available
config.openspec_enabled  = false      # always use append fallback
config.openspec_cli_path = "openspec" # or an absolute path

Key Concepts #

Tiers

Tasks are grouped into execution tiers computed from the depends_on DAG. Tier 0 has no dependencies, tier 1 depends only on tier 0, and so on. Each tier is published, executed, and merged before the next starts.

Spec deltas

When the analyzer decides iterate_spec, it produces structured requirement-level changes (add, modify, or remove) rather than free-text appends. Each delta includes an operation, section, requirement content, and rationale — keeping specs clean across iterations.

Personas, recipes & domain types

Arnold's library system is loaded from YAML files. Personas define agent behavior (Software Architect, Domain Expert, QA Analyst). Recipes define application structure templates (Web App, API Service). Domain types provide a domain-specific prompting lens (FINTECH, GAME, HEALTH, etc. — 13 built-in types). The Library Manager matches your input to the best combination via keyword matching, with generic fallbacks.

Pipeline events

An audit trail of every stage transition and decision: library selection, spec generation, task breakdown, tier execution, gate checks, analysis decisions, and lifecycle events. View via arnold log ID.

Architecture #

Key classes

  • Orchestrator — The pipeline driver. call(nl_input:, stop_after:) for new runs, resume(pipeline_run:, stop_after:) for continuation. Owns the state machine and delegates to agents.
  • AnalysisLoop — Extracted iteration logic. Runs the analyzer, interprets the decision, drives the next cycle.
  • TierExecutionEngine — Tier-by-tier execution: publish, await, gate check, merge, advance.
  • Agents — Stateless service objects with a call(**kwargs) interface. Each builds an LLM prompt, makes an API call, parses the response.
  • Providers — Pluggable backends. LLM providers handle API calls. Execution providers handle task dispatch and results. Both use a build factory pattern.
  • Library::Manager — Loads personas, recipes, and domain types from YAML. Matches via keyword overlap with generic fallbacks.

Directory structure

text 
lib/arnold_pipeline/
  agents/
    base_agent.rb          # Shared agent interface
    analyzer.rb            # Post-execution analysis & confidence scoring
    executor.rb            # Dispatches tasks to execution provider
    spec_generator.rb      # NL input → structured specification
    task_breaker.rb        # Specification → ordered task list
    tier_gate_check.rb     # Per-tier diff validation
  library/
    manager.rb             # Keyword-based retrieval
    persona.rb / recipe.rb # Data.define value objects
  prompts/                 # ERB prompt templates
  providers/
    execution/             # GitHub, Claude Code, Null
    llm/                   # Anthropic, OpenAI
  orchestrator.rb          # Main pipeline driver
  analysis_loop.rb         # Iteration logic
  tier_execution_engine.rb # Tier-by-tier loop
  configuration.rb         # Config with defaults & validation
