- **Run not found:** Clean message: `"Pipeline run #999 not found"` -- good.
- **No spec for run:** Clean message: `"No specification found for pipeline run #X"` -- good.
- **Missing required arg:** Thor's built-in message is reasonable: `ERROR: "arnold run_pipeline" was called with no arguments`.

**Empty description:** `arnold run ""` passes Thor arg validation but then crashes with a raw stack trace when the orchestrator tries to init without API key. No validation that description is non-empty.

**Input validation:** No fail-fast validation. The CLI calls `setup_standalone!` then `load_config!` then constructs the Orchestrator, which triggers API key validation deep in the provider stack. A preflight check would catch common issues (missing API key, missing repo) before any work begins.

### 2. Separation of Concerns

**Strengths:**

- CLI parsing is cleanly separated from business logic. `Cli` delegates to `Orchestrator` for pipeline execution and to ActiveRecord models for read-only queries. The CLI never contains domain logic.
- Core logic is fully usable as a Ruby library without the CLI. The `Orchestrator`, agents, and providers are plain Ruby classes with no CLI dependencies. The engine mounts into any Rails app.
- Dependency direction is correct and uni-directional: CLI → Orchestrator → Agents → Providers → External APIs. No circular dependencies detected.
- The `Executor` correctly wraps the execution provider rather than inheriting from `BaseAgent`, since it is not an LLM-based agent — good design decision.

**Violations:**

- **ARCH-SOC-001** (Low): `Cli#setup_standalone!` (cli.rb:128-142) mixes infrastructure bootstrapping (ActiveRecord connection, migrations) with CLI routing. This works but would be cleaner as a separate `StandaloneBootstrapper` class.
- **ARCH-SOC-002** (Low): `Orchestrator` at 463 lines contains both pipeline stage sequencing and significant business logic (tier gate handling, context propagation, resume inference). The class has grown organically and would benefit from extraction (see Refactoring Candidates).
- **ARCH-SOC-003** (Medium): `PipelineJob#perform` (pipeline_job.rb:5-7) creates a NEW pipeline run via `orchestrator.call(nl_input:)` instead of operating on the existing run. This means the job ignores the already-created PipelineRun record that was passed by ID, creating a double-run bug. This is a logic error, not just a SoC violation.

### 3. Extensibility

**Strengths:**

- **Provider pattern**: Both LLM and Execution providers use a `Base` abstract class + `build` factory method. Adding a new LLM provider (e.g., Gemini) requires: (1) implement `Llm::Gemini < Llm::Base`, (2) add to `Llm.build` case statement, (3) add to `VALID_LLM_PROVIDERS`. Clean and straightforward.
- **Library system**: Custom personas/recipes/domain_types can be loaded from a user-specified directory via `config.library_path`. The YAML format is documented and extensible.
- **Prompt modules**: Prompts are cleanly separated into modules with `system_prompt`/`user_prompt` class methods. New prompt variants can be added without touching agent code.
- **Dependency injection**: All agents and the orchestrator accept collaborators via constructor injection, making them testable and overridable.

**Limitations:**

- **ARCH-EXT-001** (Medium): No plugin/hook architecture. There are no before/after hooks for pipeline stages, no event bus, no middleware chain. Adding cross-cutting concerns (logging, metrics, notifications) requires modifying the Orchestrator directly.
- **ARCH-EXT-002** (Low): No custom output format system. The CLI outputs to stdout only; there is no formatter abstraction for JSON/YAML/table output modes.
- **ARCH-EXT-003** (Low): Adding a new pipeline stage (e.g., a "review" stage between execute and analyze) requires modifying `STAGES`, `STAGE_CHECKPOINTS`, and `run_pipeline!` in the Orchestrator. The stage list is hardcoded.
- **ARCH-EXT-004** (Low): The `best_match` algorithm in Library::Manager uses simple keyword counting. There is no extension point for custom matching strategies (vector DB, TF-IDF, etc.) as mentioned in the spec.

### 4. Code Quality

**Strengths:**

- **Idiomatic Ruby**: The codebase uses modern Ruby 4+ patterns consistently: `Data.define` for value objects, keyword arguments everywhere, `&.` safe navigation, heredoc prompts, frozen string literals in the entry point, pattern matching with `case/when`.
- **Custom exception hierarchy**: `ArnoldPipeline::Error < StandardError`, `ConfigurationError < Error`, `TierGateError < Error`, `TierCalculator::CycleError < StandardError`. Proper hierarchy for targeted rescue.
- **No monkey-patching**: No core class extensions or reopening of external gem classes.
- **No excess metaprogramming**: `send(:"#{stage}!")` in Orchestrator is the only dynamic dispatch, and it's constrained to the `STAGES` constant.
- **Clean value objects**: `Persona`, `Recipe`, `DomainType` use `Data.define` — immutable, with automatic `==`, `hash`, `to_s`.
- **Gemspec is reasonable**: Dependencies are version-constrained with `~>` for stability. Only 5 runtime dependencies.

**Issues:**

- **ARCH-QUAL-001** (Medium): Bare `rescue => e` in several places catches all `StandardError` subclasses indiscriminately:
  - `orchestrator.rb:68`: `rescue => e` in `run_pipeline!` — appropriate here as a catch-all with re-raise.
  - `orchestrator.rb:291-293`: `rescue => e` in `merge_results!` — swallows all errors silently (only logs warning).
  - `orchestrator.rb:298-300`: `rescue => e` in `merge_tier_results!` — same pattern.
  - `orchestrator.rb:327-329`: `rescue => e` in `run_tier_gate!` — intentionally non-fatal but very broad.
  - `github.rb:162-163`: `rescue => e` in `check_workflows_active?` — catches all errors including potential auth failures.
  - `pipeline_job.rb:8-10`: `rescue => e` — appropriate for a job error handler.

  The non-fatal rescues are reasonable design choices (gate/merge failures shouldn't crash the pipeline), but they should rescue more specific exception types (e.g., `Octokit::Error`, `JSON::ParserError`) to avoid masking unexpected bugs.

- **ARCH-QUAL-002** (Medium): `Orchestrator` at 463 lines exceeds the 200-line guideline. The class handles 4 distinct concerns: (1) stage sequencing, (2) tier execution with gate handling, (3) context propagation, (4) resume inference. See Refactoring Candidates.

- **ARCH-QUAL-003** (Low): `handle_tier_gate_failure!` (orchestrator.rb:332-399) is recursive — it calls `run_tier_gate!` which can call back into `handle_tier_gate_failure!`. The recursion is bounded by `max_tier_retries` (max depth = 5), but recursive retry logic is harder to reason about than an iterative loop.

- **ARCH-QUAL-004** (Low): `Github#fetch_results` (github.rb:52-53) calls `@client.pull_requests(@repo, state: "all")` for EVERY task. With 20 tasks, this makes 20 API calls fetching all PRs each time. This should be batched — fetch PRs once, then match.

- **ARCH-QUAL-005** (Low): `Iteration::MAX_ITERATIONS = 3` is hardcoded in the model validation (iteration.rb:9), but `Configuration#max_iterations` allows values 1-10. If `max_iterations` is set to 5, iteration validation rejects iterations 4 and 5. This is a mismatch between the model constraint and the configuration range.

- **ARCH-QUAL-006** (Info): No thread safety concerns — the pipeline is single-threaded by design. The `Orchestrator` modifies database state sequentially. However, there are no database-level locks, so concurrent pipeline runs against the same repo could conflict.

- **ARCH-QUAL-007** (Low): `Task` model uses `default_scope { order(:position) }` (task.rb:41). Default scopes are a well-known Rails anti-pattern — they apply to all queries including joins and can cause unexpected behavior. A named scope or explicit ordering would be safer.

### Refactoring Candidates

#### 1. Extract `TierExecutionEngine` from Orchestrator

**Class:** `ArnoldPipeline::Orchestrator` (orchestrator.rb:131-424)
**Rationale:** The `execute!` method and its supporting methods (`run_tier_gate!`, `handle_tier_gate_failure!`, `store_tier_context!`, `load_accumulated_context`, `build_prior_context`, `merge_tier_results!`) form a cohesive unit responsible for tier-by-tier execution. This is ~200 lines that can be extracted.

**Suggested approach:**
```ruby
class TierExecutionEngine
  def initialize(executor:, tier_gate_check:, logger:)
  def execute_tiers!(pipeline_run)
  # Contains: execute!, run_tier_gate!, handle_tier_gate_failure!,
  # store_tier_context!, load_accumulated_context, build_prior_context,
  # merge_tier_results!, tier_task_resolved?, gate_check_needed?
end
```

This would reduce Orchestrator to ~250 lines and give tier execution a clear boundary.

#### 2. Extract `ResumeInferrer` from Orchestrator

**Method:** `Orchestrator#infer_resume_stage` (orchestrator.rb:442-460)
**Rationale:** Resume stage inference is a self-contained decision function that examines pipeline state. It has its own tests and could be a standalone service object.

**Suggested approach:**
```ruby
class ResumeInferrer
  def self.call(pipeline_run) -> Symbol
end
```

#### 3. Fix PipelineJob Double-Run Bug

**Class:** `ArnoldPipeline::PipelineJob` (pipeline_job.rb:5-7)
**Rationale:** Currently calls `Orchestrator.new.call(nl_input: pipeline_run.nl_input)` which creates a second PipelineRun. Should use `orchestrator.resume` or pass the existing run through.

**Suggested approach:**
```ruby
def perform(pipeline_run_id)
  pipeline_run = PipelineRun.find(pipeline_run_id)
  if pipeline_run.pending?
    # Fresh run: set up and execute using existing record
    Orchestrator.new.call_with_run(pipeline_run)
  else
    Orchestrator.new.resume(pipeline_run:)
  end
end
```

#### 4. Batch PR Fetching in Github Provider

**Method:** `Github#fetch_results` (github.rb:44-81)
**Rationale:** Calls `@client.pull_requests(@repo, state: "all")` once per task. With N tasks, this is N identical API calls.

**Suggested approach:**
```ruby
def fetch_results(pipeline_run:, tasks: nil)
  target_tasks = tasks || pipeline_run.tasks
  all_prs = @client.pull_requests(@repo, state: "all")  # Fetch once

  target_tasks.map do |task|
    next unless task.external_id
    matching_prs = all_prs.select { |pr| ... }
    # ... rest of processing
  end.compact
end
```

#### 5. Replace Recursive Gate Retry with Iteration

**Method:** `Orchestrator#handle_tier_gate_failure!` (orchestrator.rb:332-399)
**Rationale:** Recursive method is harder to debug and reason about. An iterative retry loop with `max_tier_retries` would be equivalent and clearer.

**Suggested approach:**
```ruby
def handle_tier_gate_failure!(pipeline_run, tier_num, tier_tasks, gate_result, accumulated_context)
  max_retries.times do |attempt|
    # create corrective tasks, execute, re-gate
    break if new_gate_result&.dig("pass")
  end
  # If still failing after max retries, pause
end
```

#### 6. Harmonize Iteration MAX_ITERATIONS with Configuration

**Files:** `iteration.rb:9`, `configuration.rb:93-96`
**Rationale:** Model hardcodes `MAX_ITERATIONS = 3` in validation; config allows 1-10. These must agree.

**Suggested approach:** Remove the hardcoded constant from the Iteration model. Either validate against the current configuration value or remove the iteration number ceiling from the model validation entirely (the Orchestrator already enforces the limit via `analysis_loop!`).
